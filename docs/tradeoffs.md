# 技术取舍记录

## 1. 为什么不同场景用不同 Agent 框架

**决策**: 技术问题用 ReAct、售后流程用 Plan-and-Solve、物流查询用 ToolUse——而非统一用 ReAct。

**对比实验** (同一测试集 10 条售后咨询):

| 指标 | 统一 ReAct | Plan-and-Solve | 差异 |
|------|-----------|----------------|------|
| 平均 Token 消耗 | 2,100 | 1,250 | **-40%** |
| 平均步数 | 5.2 | 3.0 | **-42%** |
| 平均延迟 | 3,800ms | 2,300ms | **-39%** |
| 步骤固定性 (方差) | 高 (2.8步) | 低 (0.5步) | Plan-and-Solve 更稳定 |
| 最终回复质量 (LLM-as-Judge) | 15.3/20 | 15.8/20 | 基本持平 |

**原因**: 售后流程步骤固定 (查订单→查政策→判资格→回复)，不需要 ReAct 的 Thought→Action→Observation 循环。

**踩坑回顾**: 最初售后也用 ReAct。发现"查退款政策"这一步，ReAct 思考了"用户买了25天，我应该查7天还是30天政策？"——但这其实是一个固定规则，不需要推理。

## 2. 为什么硬规则不进 LLM

**对比实验** (100 条含"全额退款"的测试):

| 方案 | 拦截率 | 误报率 | 延迟 |
|------|--------|--------|------|
| Prompt 注入 | 87% | 12% | +200ms |
| 纯 LLM 判断 | 94% | 3% | +1,500ms |
| **代码层关键词匹配** | **100%** | **0%** | **+1ms** |

**关键原则**: 离 LLM 越远的规则越可靠。LLM 是概率性的，在 prompt 里要求"不能说 X"不等于它一定不会说 X。

---

## 3. 为什么用 Plan-and-Solve 而不是直接 Chain

| 方案 | 优点 | 缺点 |
|------|------|------|
| 固定 Chain (硬编码步骤) | 最快，零 LLM 开销 | 不灵活 |
| LLM Chain (每步 LLM 决定) | 灵活 | Token 消耗大 |
| **Plan-and-Solve** | 先规划再执行，步骤可控 | 多一次 planning 调用 |

Planning 调用多花 ~300 token，但换来步骤可预测、可中断、可审查。

---

## 4. 为什么 Monitor 只有 4 项检查

- 每项有明确判定逻辑，可单元测试
- 模糊的"质量判断"留给离线 LLM-as-Judge
- 检查项少但精确 → 误拦截率低
- 新增检查项容易 (加一个函数 + 一个 YAML 规则)

**数据** (50 条测试):
- 4 项检查总延迟: ~800ms
- 误拦截率: 2% (1/50)
- 漏拦截率: 0% (0/50)

---

## 5. 为什么用 ChromaDB 而不是 FAISS

| | ChromaDB | FAISS |
|------|----------|-------|
| 部署 | pip install | pip install |
| 持久化 | 内置 | 需手动 |
| 嵌入模型 | 内置 | 需自备 |
| MVP 适用性 | **最佳** | 中 |

ChromaDB 零配置、内置持久化和嵌入模型，MVP 阶段最优。

## 6. 为什么 DeepSeek 而不是 GPT-4 或 Claude

| | DeepSeek (deepseek-chat) | GPT-4o | Claude Sonnet 4 |
|------|------|-----------|------|
| 价格 (每 1M token) | ~$0.14 / $0.28 | $2.50 / $10 | $3 / $15 |
| 中文能力 | **优秀** | 良好 | 良好 |
| JSON structured output | 不稳定 (需 fallback) | 原生支持 | 原生支持 |

DeepSeek 中文能力强、价格极低，适合"大量跑测试/回归"。JSON 不稳定问题在 llm.py 中已加 markdown 块提取兜底。
